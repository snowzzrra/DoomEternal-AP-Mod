# Reports: implantação sem domínio próprio

Este checkout tem endpoint=null. O maintainer precisa implantar e qualificar o serviço para habilitar envio. Este guia fornece operações; não cria infraestrutura nem issues.

## 1. Criar e instalar o GitHub App

Na conta que administra snowzzrra/DoomEternal-AP-Mod, abra https://github.com/settings/apps/new.

- Escolha um nome disponível, por exemplo Doom Eternal AP Reports.
- Homepage URL: https://github.com/snowzzrra/DoomEternal-AP-Mod.
- Deixe callback/OAuth sem uso e desmarque Webhook → Active.
- Repository permissions: Issues = Read and write; Metadata = Read-only obrigatório. Deixe as outras permissões e eventos sem acesso.
- Se o repositório pertence à sua conta pessoal, selecione Only on this account para instalação.

Crie o App. Anote o App ID, que difere do Client ID. Em Install App, escolha Only select repositories e apenas DoomEternal-AP-Mod. Anote o installation ID da URL em Settings → Applications → Installed GitHub Apps → Configure.

Em General → Private keys, gere e baixe a chave PEM. Guarde-a fora do checkout e do pacote. Você colocará seu conteúdo apenas no armazenamento de segredos do servidor. O backend solicita tokens limitados ao repositório fixo e Issues/write. Jogadores não precisam de conta ou PAT.

Documentação: https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app e https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps.

## 2. Criar um Web Service Node no Render

Abra https://dashboard.render.com → New → Web Service. Conecte o repositório e selecione a branch publicada pelo maintainer com o server.cjs qualificado deste candidato. Registre o SHA. Publicar essa branch exige a autorização de commit/push do projeto.

- Runtime: Node.
- Root Directory: tools/report_backend.
- Build Command: node --check server.cjs.
- Start Command: node server.cjs.
- Instance: uma instância paga com suporte a Persistent Disk; confira o preço no painel.
- Réplicas: uma; a coordenação usa arquivos exclusivos nesse volume.
- Health Check Path: /health.
- Auto-deploy: desabilitado durante qualificação; selecione o SHA aprovado.

O Render fornece https://<nome-do-servico>.onrender.com e certificado TLS. Você pode usar essa URL sem comprar domínio. O filesystem gratuito/efêmero perde reservas em restart/deploy e não atende a idempotência deste serviço.

Documentação: https://render.com/docs/web-services e https://render.com/docs/disks.

## 3. Configurar disco, chave e ambiente

Em Advanced ou na aba Disk, adicione um Persistent Disk de 1 GB com mount path /var/data. Só os arquivos sob esse mount persistem. Preserve reservas, digests e URLs nos backups/snapshots; apagar uma reserva apaga sua proteção contra duplicação.

Na aba Environment → Secret Files → Add Secret File, use Filename=github-app.pem e coloque o conteúdo completo da chave PEM no painel. O runtime Node nativo acessa esse arquivo em /etc/secrets/github-app.pem.

Configure as variáveis:

GITHUB_APP_ID=<App ID numérico>
GITHUB_INSTALLATION_ID=<installation ID numérico>
GITHUB_APP_KEY_FILE=/etc/secrets/github-app.pem
REPORT_DATA_DIR=/var/data/reports
REPORT_TRUSTED_PROXY_HOPS=0
NODE_VERSION=24
PORT=8080

Confirme nos logs que o processo consegue criar /var/data/reports. Mantenha a chave no servidor, fora de Git, YAML, launcher, ZIP, prints ou conversa.

Documentação: https://render.com/docs/configure-environment-variables.

## 4. Qualificar HTTPS e ingress

Faça o deploy e abra https://<nome-do-servico>.onrender.com/health. Espere HTTP 200 com {"status":"ready"}. Isso verifica a partida; a issue consentida da etapa 6 verifica o App e o acesso ao GitHub.

O Node escuta 0.0.0.0:8080. Mantenha acesso público pelo ingress HTTPS, sem exposição direta dessa porta. O serviço aceita POST /v1/reports, application/json, até 32768 bytes; limita oito requests simultâneos e dez novos reports/hora por endereço.

REPORT_TRUSTED_PROXY_HOPS=0 ignora X-Forwarded-For: clientes atrás do mesmo socket do proxy compartilham dez reports/hora. Antes dos cinco testers, confirme a topologia do ingress e a posição do IP real. Para um único proxy confiável, configure 1; para dois hops comprovados, configure 2. O algoritmo acrescenta o socket peer à cadeia e seleciona o endereço à esquerda desses hops. Endereço ausente/inválido recebe erro quando configurado. Essa configuração exige quantidade comprovada de proxies e ausência de acesso direto ao backend. Cadeia incerta mantém a qualificação pendente.

test_server.cjs exercita cinco clientes, quotas, concorrência, restart, busca tardia e token+issue frios com transport fake. Esses testes locais não demonstram o ingress implantado.

## 5. Configurar o endpoint e congelar o produto

Após HTTPS, persistência e ingress qualificados, edite a fonte canônica data/report_endpoint.json:

{"schema_version":1,"endpoint":"https://<nome-do-servico>.onrender.com/v1/reports"}

Execute o pipeline oficial para gerar o pacote. Registre SHA do backend, URL, App/installation IDs públicos, hash do launcher e manifest. Confirme a mesma URL na fonte e no produto congelado. Preserve a integridade do pacote; não edite sua configuração embutida após registrar o manifest.

O endpoint fica null até essa etapa. O cliente usa 40 segundos; cada chamada GitHub usa 12 segundos e o token frio precede o POST de issue. Timeout mantém rascunho, chave e reserva; ele não autoriza outro POST.

## 6. Uma issue real e retry, com autorização

Peça ao maintainer autorização para uma issue identificada, por exemplo [RMO6][report-qualification][data/hora]. No launcher congelado, abra Help → Report a Problem. Revise título, descrição e diagnostics sanitizados. Confirme o envio. Anote a URL real em snowzzrra/DoomEternal-AP-Mod e a chave; exportação ou HTTP genérico não provam criação.

Reenvie o mesmo payload/chave e reinicie o serviço antes de outro retry. Espere a mesma URL e conte uma issue. Payload diferente com a mesma chave recebe conflito. Em timeout/busca sem resultado, espere e use Retry Reviewed Report ou reabra o diálogo. O backend pesquisa o marcador exato, preserva a reserva e não repete o POST. Preserve as reservas durante recuperação.

O ZIP permanece local; o serviço publica o texto revisado e tails limitados. Ele não envia saves, PEM, tokens ou ZIP como suposto attachment pela API. Serviço/GitHub indisponível mantém material local e tentativa pendente. Após URL confirmada, Start New Report arquiva o rascunho confirmado e cria outra chave.

## 7. Operar e revogar

Mantenha uma réplica, backups e orçamento. Para revogar uma chave, substitua o Secret File e redeploy o backend. Confira installation ID ao reinstalar o App. Preserve reservas e URLs em incidentes/restaurações. Se o serviço não puder preservar idempotência, configure endpoint=null e recongele o produto.
